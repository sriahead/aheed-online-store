# P4b — Staff order status transitions & delivery emails (requirements / acceptance criteria)

Closes P4 (epic #87), issue **#125**. Builds on P4a (`specs/2026-08-11-p4a-order-history/`), which
made order status visible, and on ADR-004 slice 3a's `VendorMembership`, whose first real consumer
this is. A vendor-role-gated staff queue at `/staff/orders` advances an order along
`CONFIRMED → OUT_FOR_DELIVERY → DELIVERED`, writing an `OrderStatusEvent` attributed to the acting
staff member and emailing the customer at each step. One additive, nullable migration.

## Transition rules (pure, no DB)

R1. `lib/order-status.ts` contains no I/O: `getPrisma`, `@prisma/client`, `fetch(`, `cookies(` and
    `headers(` do not appear as code in the file, and its unit tests pass with no database
    reachable.
R2. `canTransition("CONFIRMED", "OUT_FOR_DELIVERY")` and `canTransition("OUT_FOR_DELIVERY",
    "DELIVERED")` both return `true`.
R3. `canTransition` returns `false` for every ordered pair of the five `OrderStatus` values other
    than the two in R2 — including every `PENDING_PAYMENT → *` pair, every `DELIVERED → *` and
    `CANCELLED → *` pair, the rung-skipping `CONFIRMED → DELIVERED`, every backwards pair, and every
    self-pair such as `CONFIRMED → CONFIRMED`.
R4. `canTransition` returns `false` and `nextStatus` returns `null` when `from` is a string that is
    not one of the five `OrderStatus` values (e.g. `"NOT_A_STATUS"`), without throwing.
R5. `nextStatus` returns `"OUT_FOR_DELIVERY"` for `"CONFIRMED"`, `"DELIVERED"` for
    `"OUT_FOR_DELIVERY"`, and `null` for `"PENDING_PAYMENT"`, `"DELIVERED"` and `"CANCELLED"`.
R6. For every one of the five `OrderStatus` values `s`, `nextStatus(s)` is non-null **if and only
    if** `canTransition(s, nextStatus(s))` is `true` — the two exports cannot disagree.

## Schema & migration

R7. `prisma/schema.prisma`'s `OrderStatusEvent` model declares `createdByUserId String?` and a
    `createdBy User?` relation; the field is optional and no other model in the file is modified by
    this slice.
R8. A single new migration directory exists under `prisma/migrations/` whose `migration.sql`
    contains an `ADD COLUMN` for `createdByUserId` and contains no `DROP`, no `SET NOT NULL` and no
    `ALTER TYPE` statement.
R9. The relation is declared `onDelete: SetNull`, so deleting a `User` leaves their
    `OrderStatusEvent` rows in place with `createdByUserId` null.
R10. `prisma migrate deploy` applies the migration to a database already holding P3-era data
     without error, and every `OrderStatusEvent` row that existed beforehand has
     `createdByUserId IS NULL` afterwards.
R11. `prisma migrate status` reports no pending migrations and no drift after R10.

## `advanceOrderStatus` service

R12. `advanceOrderStatus` is exported from `lib/repositories/orders.ts` and takes `prisma`,
     `vendorId`, `orderNumber`, `toStatus` and `actor` as explicit arguments, so it is callable from
     a plain `tsx` script with no Workers request context.
R13. `advanceOrderStatus` returns a result object and does not throw on a rejected transition:
     success is `{ ok: true, order }` where `order` carries `orderNumber`, `buyerEmail`, `items` and
     the money fields; rejection is `{ ok: false, reason }` with `reason` one of `"not-found"` or
     `"illegal-transition"`.
R14. A legal advance sets `Order.status` to `toStatus` **and** creates exactly one new
     `OrderStatusEvent` row whose `status` equals `toStatus` and whose `createdByUserId` equals the
     acting user's id.
R15. The `note` written on a staff transition is generated by this slice's own code from the target
     status, and P4b ships **no** input, textarea or action parameter through which a staff member
     can supply free text for that column — the queue's only control is the advance button.
R16. An illegal advance (e.g. `PENDING_PAYMENT → DELIVERED`, or `CONFIRMED → DELIVERED`) returns
     `{ ok: false, reason: "illegal-transition" }` and leaves `Order.status` unchanged with **no**
     new `OrderStatusEvent` row written.
R17. Calling `advanceOrderStatus` with the `vendorId` of a vendor that does not own the order
     returns `{ ok: false, reason: "not-found" }` and writes nothing — the same result an unknown
     order number produces.
R18. Calling `advanceOrderStatus` twice in succession with the same `orderNumber` and `toStatus`
     returns `{ ok: true }` then `{ ok: false, reason: "illegal-transition" }`, and the order has
     exactly **one** `OrderStatusEvent` row for that status — the second call writes nothing.
R19. The status update is issued as a conditional write whose `where` clause includes both
     `vendorId` and the previously observed `status`, and the transaction callback in
     `advanceOrderStatus` contains no `fetch(` call and no email send.

## Staff queue route & action

R20. `GET /staff/orders` with no session redirects to `/login`.
R21. `GET /staff/orders` as a signed-in user holding no `VendorMembership` for the current vendor
     and no platform `ADMIN` role returns a page containing a staff-only refusal message and
     containing no order number.
R22. `GET /staff/orders` as a user with a `STAFF` `VendorMembership` for the current vendor returns
     200 and lists that vendor's orders whose status is `CONFIRMED` or `OUT_FOR_DELIVERY`, newest
     first, and lists no order whose status is `PENDING_PAYMENT`, `DELIVERED` or `CANCELLED`.
R23. The queue is keyset-paginated on `(createdAt, id)` with a bounded page size and a link to the
     next page — never `OFFSET`, and never a silently truncated list, so an actionable order beyond
     the first page is still reachable.
R24. `/staff/orders` served on one vendor's host contains no order number belonging to the other
     seeded vendor.
R25. `app/(storefront)/staff/orders/page.tsx` sets `export const dynamic = "force-dynamic"` and the
     page reuses `components/orders/OrderStatusBadge` rather than declaring a second status-badge
     implementation.
R26. The advance server action in `features/orders/` calls `requireVendorRole` itself; a POST of the
     action's payload carrying a valid `orderNumber` but sent with no session, or with a session
     holding no membership, does not change that order's status.
R27. A POST of the action's payload whose `toStatus` field is a value that is not a legal next step
     for that order's persisted status (including a value that is not an `OrderStatus` at all) does
     not change the order's status and writes no `OrderStatusEvent` row.
R28. Advancing an order from `/staff/orders` changes its status and the new step then appears on
     that customer's own `/account/orders/{orderNumber}` timeline (P4a's page, unmodified by this
     slice).

## Customer emails

R29. `sendOrderStatusEmail` does not throw when the email service rejects: with a deliberately
     broken `RESEND_API_KEY`, a legal advance still commits the status change and the
     `OrderStatusEvent` row.
R30. A legal advance to `OUT_FOR_DELIVERY` and a legal advance to `DELIVERED` each attempt exactly
     one email send, addressed to the order's `buyerEmail`, with the subject naming the vendor's
     `senderName` from `fetchVendorProfile` rather than a hardcoded store name.
R31. No email send is attempted for a rejected transition, and the `CONFIRMED` status produces no
     send from this slice's code path (P3c's confirmation email remains the only one).
R32. **Delivery to a real inbox is not verifiable in any environment** (#104 — Resend has no
     verified sending domain). R30/R31 are satisfied structurally, and `validation.md` records real
     delivery as unverified with that reason rather than as passing.
