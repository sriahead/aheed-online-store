# #927 — Staff button to run net-content suggestions (build notes)

Written at the end of Build, before the Clear. Branch `feature/927-net-content-suggest-button`, cut
from `origin/staging` at `135fbe2`. Spec commit `c981e03`; build commit `b06f055`.

## What changed and why

- **`lib/net-content-suggestions-service.ts`** (the existing request-scoped facade for `#900`)
  gains `STAFF_RUN_PRODUCT_LIMIT = 10`, `STAFF_RUN_NEURON_BUDGET = 150`, the result type
  `StaffNetContentRunResult` and `runNetContentSuggestionsForVendor(vendorId)`. It is the script's
  wiring (`scripts/suggest-net-content.ts`, `main()`), moved behind a vendor id:
  - model resolution comes first, then the rate lookup, returning `unpriced-model` before any
    query (R3);
  - the eligibility list (`includeAttempted: false`, limit 10) comes next, returning
    `nothing-eligible` before any model is built (R4);
  - `getVendorConfig` supplies `storeDescription`;
  - `getStorage()` supplies the photo loader, with the same `headObject` + `getObject` pair as the
    script;
  - `createNetContentSuggestion` is called through `getPrisma()`;
  - finally the unchanged `runNetContentSuggestions` runs.
- **`lib/net-content-review-form.ts`** (the plain module holding the review form's state) gains
  `describeStaffNetContentRun`, with the six exact strings from R6. It type-imports the result type
  from the service. The import is type-only, so the client component that imports this module pulls
  in no `lib/db` code.
- **`features/admin/net-content-suggestions.ts`** gains `suggestNetContent`:
  `requireVendorRole("ADMIN")`, then the service with `auth.vendorId`, then `revalidatePath` only
  for a `ran` result, then the message. The file still exports only async functions, asserted by
  the new test.
- **`components/staff/SuggestNetContentForm.tsx`** (new) has the same shape as
  `ProposeSynonymsForm`: one `<form>`, `useActionState`, inline `role="alert"` / `role="status"`.
- **`app/(admin)/staff/net-content/page.tsx`**:
  - renders the form above the pilot summary when `auth.via !== "STAFF"`, or otherwise the exact
    staff sentence;
  - the empty-queue text is now "New ones appear here when a store admin asks the AI.";
  - the header comment names both entry points.
- **Docs:**
  - `docs/staff-playbook/staff-tabs-guide.md` is now 2.8.0. The "Typical workflow" paragraph of
    the net-content section is rewritten.
  - `specs/architecture.md` is now 1.37.0. The `#900` "Offline and proposed" bullet names the
    second entry point.
  - `docs/developer-portal/env-setup.md` is now 1.15.0, with a new "staff button" bullet in the
    AI net-content section.
  - `ARTIFACT_INDEX.md` and `app/(admin)/staff/runbook/docs.ts` were regenerated by
    `kms:build-index`.
- **Tests (new):**
  - `tests/net-content-staff-run.test.ts` covers R1, R3–R6 in 13 tests;
  - `tests/net-content-suggest-action.test.ts` covers R7–R9 in 6 tests.

## Decisions taken during the build

- **`getVendorConfig` is called only after the eligibility list is non-empty.** This saves a query
  on the `nothing-eligible` path. The spec did not order these.
- **The `ran` → message mapping treats any outcome other than `transport-errors` and
  `budget-reached` as `completed`.** `RunSummary.outcome` can in type terms be `not-configured`
  inside a `ran` result, but the service never produces that, since R5 maps it out first. No extra
  branch was added for an impossible case.
- **The form's intro text** reads "Ask the AI to suggest a pack size for up to 10 products that
  don't have one yet. Suggestions arrive below for review; nothing changes on a product until you
  accept it." R10 fixes only the button labels, so this wording is a build choice. It is
  vendor-neutral, and `tests/vendor-neutral-copy.test.ts` passes.
- **The staff sentence is a plain `<p>`,** not a `PanelRefusal`. The viewer is allowed on the page,
  only not the button, so it is not a refusal branch.

## Known-shaky areas

- **Nothing here has run on a Worker yet.** Every check so far is a unit test with mocks. The
  first real exercise of `createWorkersAiNetContentSuggester` inside a request (not in the Node
  script) is R13 under `npm run preview`. Watch for these:
  - **Credentials:** `getAiEnv()` must read `CLOUDFLARE_ACCOUNT_ID`/`CLOUDFLARE_API_TOKEN` from
    `.dev.vars` under preview. If they are absent there, the button answers "The AI isn't set up
    for this store…". That is correct behaviour, but it proves nothing about R13.
  - **Click duration:** about 10 × 1.2 s when healthy. The suggester's 60 s per-call timeout means
    a stalled Workers AI can hold a click much longer. That is expected per `plan.md`, not a
    defect.
- **R14 depends on eligibility excluding any product with any suggestion row** (the
  `none: {}` branch of `buildEligibleProductWhere`). That is `#900` code, unit-tested there, and
  unchanged here.
- **The full vitest suite had one failure: `tests/vendor-neutral-copy.test.ts` timed out at 5 s
  under full-suite load** (190/191 files, 2506/2507 tests). The file passed alone in about 1 s,
  2/2. This is the known full-suite timeout pattern tracked in `#538`, which already lists this
  file. It is not caused by this slice. CI is ground truth for R20.
- **`kms:check-generated` reports "stale" until the regenerated files are committed.** It compares
  against the index, not the working tree. It passed after commit `b06f055`.
- **R13–R15 need `demo-store-admin@example.com` and `demo-staff@example.com` on dev.** Their
  presence on dev was not checked at Build.
- **Deferred and filed:** `#928`, sending the product description to the model, found by `#901`.
  `#697` keeps the not-applicable marker and loose-by-weight products.
