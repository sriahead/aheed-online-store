# Telegram alerts for order-related inquiries (validation)

> **Testing Strategy (Lean 80/20 Model)**
> Provide enough testing to give confidence without creating unnecessary or duplicate tests. Avoid testing the same behaviour multiple times at different levels unless doing so provides additional confidence.
>
> **The Main Principle:**
> - **Build:** Did we build the component correctly?
> - **Validate:** Does the feature work correctly in the real system?
> - **Release:** Is the complete system safe, reliable, and ready for users?

## Testing Areas

Every feature should have appropriate **Unit** and **Integration** testing, followed by relevant validation testing. Broader testing mainly happens before release. However, testing is risk-based: features involving auth, payments, UI changes, performance-sensitive APIs, databases, or external dependencies require additional relevant testing earlier.

1. **Unit Testing**: every feature. Isolated logic, utilities and components.
2. **Integration Testing**: every feature, including contracts. The component with its immediate dependencies.
3. **System / End-to-End Testing**: critical journeys. The feature in the real system.
4. **Regression & Acceptance Testing**: before release or when core flows change.
5. **Performance & Resilience Testing**: before release, or for performance-sensitive APIs.
6. **Security & Accessibility Testing**: before release, or earlier for auth, payments or UI.

## Before you start

- **Run the suite on its own, capped:** `npx vitest run --maxWorkers=4`. If failures move between
  runs and take 5-9 s each, that is the loaded-machine artefact (CLAUDE.md), not a regression.
- **Check the database target before any Prisma CLI command.** Check `DIRECT_URL` and
  `DATABASE_URL` one at a time (`if printenv DIRECT_URL >/dev/null 2>&1; then ...`). If either is
  set, prefix Prisma commands with `env -u DIRECT_URL -u DATABASE_URL`. Read the datasource host
  that `prisma migrate status` prints: it must be the dev host from `secrets/`, not production.
  Applying the migration to dev (`prisma migrate deploy`) is a command the owner runs; hand it over
  as a `! <command>`.
- **Use `npm run preview` for live rows, never `npm run dev`**, which cannot load the WASM Prisma
  engine.
- **A Server Action can be driven with `curl`** (post the multipart form with the `Next-Action`
  header, taking its id from the rendered page) or through Chrome automation. Record which you used.
- **R19 needs the owner's bot token.** If `TELEGRAM_BOT_TOKEN` is not available, report R19 as
  **BLOCKED (owner resource missing)**. Blocked is not a pass, and the other rows still run.
