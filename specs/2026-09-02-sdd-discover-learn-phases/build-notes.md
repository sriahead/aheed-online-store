# DISCOVER and LEARN — milestone-level SDD phases (build notes)

Written at the end of Build, **before** the Clear. This is the one artifact the Clear bets on:
the validating context is fresh and has only the spec, the artifact, and this file.

**Read this first: the build preceded the spec.** The human directed the change in conversation, the
implementation was written, and only then was `#550` opened and this spec written against the built
artifact. That is Gate 1 applied retroactively, disclosed in `plan.md` and repeated here because a
validator has no other way to know. The practical consequence for validation: `requirements.md`
describes what exists rather than what was aimed at, so a passing row proves the artifact matches
its description — it does not independently prove the description was well chosen. R13, R15 and R17
are the rows that guard against the spec having been quietly widened to fit what got built.

## Decisions taken during the build

**Two append-only logs, not one file per milestone.** A file per milestone would add a KMS artifact
at every close, growing `ARTIFACT_INDEX.md` and `docs.ts` indefinitely. Rejected in favour of two
stable files whose front-matter `version` and `updated` are bumped per entry.

**`docs/`, not `specs/`.** `specs/` holds dated, one-time slice folders; these two logs are standing
documents that accumulate. `docs/` is where persistent reference knowledge already lives.

**First-class KMS front-matter rather than omitting it.** Omitting it would keep the files out of
`ARTIFACT_INDEX.md` and out of the internal docs site, at the cost of making them undiscoverable —
which is the exact failure this repo has already paid for more than once. The cost accepted is that
every research entry must clear `kms:validate` and the Nextra build.

**The discovery log was seeded with three real findings rather than shipped empty.** An empty file
plus a template demonstrates nothing about whether the format survives contact with a real finding.
The three seeded are genuinely unowned, and `plan.md` and R15 both state explicitly that they do not
become scope.

**Discover before Learn at milestone close.** Stated as a rule with its reason in the doc, so a
future reader does not reorder it as an arbitrary preference.

**Neither phase is a gate.** The alternative — making a retrospective a merge requirement — was
rejected on the grounds that evidence a merge depends on gets written to pass rather than to be
true. This is the decision most likely to be revisited, and `#551` is where that conversation lands.

## Deviations from the spec

**None**, in the ordinary sense — but the ordering is itself the deviation worth naming: the spec was
written after the artifact, so it cannot have been deviated from during a build that had already
happened. See the disclosure at the top of this file. No requirement was written to describe
something the artifact does not do, and no part of the artifact is undescribed by a requirement.

## Known-shaky areas

**The MDX pipeline is the real risk, and it is the one thing the root gates cannot see.** Research
prose quotes UI labels and cites percentages — precisely the bare-curly-brace and
bare-`<`-before-a-digit traps that have broken `deploy-docs-internal` three times. R9 was run during
Build and passed (exit 0, 145 pages prerendered, all three research docs among them), but any later
edit to these files reopens the exposure, and no root check will report it.

**Nothing mechanically enforces the milestone-close step.** A milestone can close with a roadmap
change-log row and no retrospective entry, and `sdd:audit` will not notice. This is a known,
deliberate gap deferred to `#551` by the human's ruling; it is not an oversight to be fixed at
`/fix`.

**The process has never been executed.** Both commands are written and neither has run at a real
milestone close. The first genuine test is P9's close, and the entry templates are the part most
likely to need revision once a real entry is written against them.

**`kms/site-internal/next-env.d.ts` is rewritten as a side effect of running the Nextra build** and
was reverted during Build. Re-running R9 at Validate will dirty it again — revert it rather than
committing it.
