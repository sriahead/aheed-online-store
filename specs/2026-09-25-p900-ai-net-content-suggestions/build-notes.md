## What changed and why

- **Schema** (`prisma/schema.prisma`, migration
  `prisma/migrations/20260925150000_p900_net_content_suggestions/`). `ProductImage.source`
  (`ProductImageSource`, default `UNKNOWN`), plus `NetContentSuggestion` and its three enums (R1,
  R2). The migration was generated by a datamodel diff against the staging schema, not by
  `migrate dev` (the `#895` dev checksum-drift trap), then read before applying. It is additive
  only: `CREATE TYPE`, `ADD COLUMN … DEFAULT 'UNKNOWN'`, `CREATE TABLE`, FKs and indexes. No
  `DROP`, no `UPDATE`, no `pg_trgm` change. It is applied to dev.
- **Image provenance** (R4–R8). `lib/repositories/products.ts` writes `STAFF_UPLOAD` in
  `addProductImage` and in both branches of `setPrimaryProductImage`.
  - `runProductImagePipeline` returns `source`, and `saveGeneratedProductImage` requires one. All
    four callers pass it.
  - The seed writes `PLACEHOLDER`.
  - Staff mark a photo as confirmed, or withdraw it, from `ProductImageManager` through the new
    `toggleConfirmedPhoto` action in `features/admin/product-image.ts`.
  - The source values are mirrored as a plain type in `lib/product-image.ts`, the same way
    `unit-price.ts` mirrors `NetContentUnit`, so pure code and tests don't import Prisma.
- **Suggester** (`lib/net-content-suggester.ts`, R9–R11). One interface and a Workers AI REST
  implementation. The reply validator is pure. This is the only file that builds a net-content AI
  request.
- **Label check** (`lib/net-content-label-check.ts`, R12). Pure and deterministic. Compares the
  suggestion with a price per kg/litre or per stated pack on the unit label.
- **Run** (`lib/net-content-run.ts` + `scripts/suggest-net-content.ts`, R13–R16). The loop takes
  its dependencies as parameters, so the script is only flag parsing and wiring and the loop is
  unit-tested with stubs. Eligibility lives in `lib/net-content-eligibility.ts`.
- **Review queue** (R17–R24). `app/(admin)/staff/net-content/page.tsx`,
  `components/staff/NetContentReviewRow.tsx`, the actions in
  `features/admin/net-content-suggestions.ts`, and the repository
  `lib/repositories/net-content-suggestions.ts` with its facade
  `lib/net-content-suggestions-service.ts`.
  - Accept and Edit write the product and the suggestion in one `getPrismaWs()` transaction.
  - Edit reuses the product form's net-content parser, now exported from `lib/catalogue-form.ts`.
  - The page composes image URLs and display strings on the server, so the storage signer never
    reaches the client bundle (same split as the product page).
  - The pilot summary is pure (`lib/net-content-pilot-summary.ts`).
  - Nav, hub and `staff-tabs-guide.md` are all updated, and the refusal branch renders
    `PanelRefusal`.
- **Persistent docs.** `specs/architecture.md` 1.33.0 adds the net-content paragraph to the AI
  rule (R25). `docs/developer-portal/env-setup.md` documents `NET_CONTENT_AI_MODEL` and the run
  command (R26).

### R27 — the real image call (2026-09-25, dev credentials, Workers AI REST API)

Build sent the Open Food Facts front-of-pack photo of Nutella (barcode `3017620422003`, OFF
quantity "400 g") in two encodings: the original JPEG (33,108 bytes) and a WebP re-encode
(17,650 bytes). The call went to `POST …/accounts/<id>/ai/run/@cf/google/gemma-4-26b-a4b-it`,
with this body shape (the one the suggester now sends):

```json
{
  "messages": [{ "role": "user", "content": [
    { "type": "text", "text": "<prompt>" },
    { "type": "image_url", "image_url": { "url": "data:image/webp;base64,<bytes>" } }
  ]}],
  "max_tokens": 200
}
```

- **WebP: accepted.** HTTP 200 in ~3.2 s. The content was
  `{"amount": 400, "unit": "GRAM", "evidence": "400G"}`, correct.
- **JPEG: accepted.** HTTP 200 in ~1.8 s, the same answer, 355 input / 124 output tokens, 6.6
  neurons.
- The response is OpenAI-shaped: `result.choices[0].message.content`, `finish_reason`, and
  `result.usage.{prompt_tokens, completion_tokens, neurons}`. The served model id is reported as
  `@cf/google/gemma-4-26b-a4b-it-external`.
- Both calls ran with Gemma's **default reasoning on**, before the reasoning-off change below. An
  image call **with reasoning off** has not been made. R29 is the first time that combination
  runs.

## Decisions taken during the build

- **Gemma 4 runs with reasoning off**, set in a per-model table
  (`NET_CONTENT_MODEL_REQUEST_OPTIONS` in `lib/net-content-suggester.ts:52`:
  `chat_template_kwargs: { enable_thinking: false }`). With the default reasoning on, every
  ambiguous product (`Whole Milk / 2pt`, `Still Water 6 x 1.5L`, `Fast Phone Charger`) reasoned
  until the token ceiling and returned **no content**, at 800 tokens and again at 2,500 (25–71
  neurons a call).
  - `reasoning_effort: "low"` did not help.
  - With reasoning off, the same calls answer in ~50 tokens at ~4–5 neurons.
  - It's data beside the model id, not a code branch, so the design stays model-agnostic. A model
    not in the table gets no extra fields.
- **`NET_CONTENT_MAX_TOKENS = 800`.** Reasoning tokens count toward `max_tokens` on this model, so
  this is a ceiling on spend as well as on the answer.
- **The prompt forbids conversion and multiplication** (`lib/net-content-suggester.ts:135-136`).
  With reasoning off, Gemma confidently answered **568 ml for "2pt"**, which is wrong: 2 pints is
  about 1,136 ml. The prompt now asks for `{"amount": null}` when the size is only in
  pints/oz/lb, or when working it out needs multiplication (`6 x 1.5L`). Staff enter those by
  hand. The result is fewer suggestions but no confident wrong ones.
- **The source enum is mirrored as a plain TS type** in `lib/product-image.ts`, following
  `unit-price.ts`, rather than importing `@prisma/client` into pure modules.
- **Eligibility is split in two pure functions** (a Prisma `where` builder plus a per-product photo
  pick) so R14 is unit-testable without a database.
- **Default neuron budget is 5,000**, half the shared 10,000/day free allowance.

## Deviations from the spec

- **A reply cut off at the token ceiling writes no row (it counts as failed).** R15 says "every
  **reply** produces exactly one `NetContentSuggestion` row", which would make a truncated reply
  `NO_ANSWER`.
  - **What changed:** `finish_reason === "length"` now returns a `transport-error`
    (`lib/net-content-suggester.ts:273-280`). The product is not marked attempted and is retried on
    a later run.
  - **Why:** `NO_ANSWER` permanently marks a product attempted, so a budget artefact would have
    hidden the product from every future default run. Build found and deleted five dev-only rows
    stored that way.
  - **Cost:** the truncated call's usage still counts toward the budget (fixed before Validate,
    see "Fixed before Validate" under Known-shaky areas).
- **The prompt's multipack rule narrows the plan's stance.** `plan.md` ("Deliberately excluded")
  says that for multipacks "the model proposes and staff decide". The prompt now tells the model to
  give no answer when the size needs multiplying (`6 x 1.5L`). No rule is encoded in the
  *validator*, but the model is steered away from proposing. Reason: the 568 ml error above. This
  is revisited from the pilot's numbers (`#901`).

## Known-shaky areas

1. **Fixed before Validate: a truncated call's neurons were not counted toward
   `--neuron-budget` (R16).** Found while writing these notes, and fixed in the same Build
   context at the owner's direction (2026-09-25) rather than left for Validate to fail.
   - **The defect:** the `transport-error` result carried no `usage`, so the run loop added
     neither tokens nor neurons for a truncated reply. Yet a truncated call is the most expensive
     kind: it spends the whole 800-token ceiling, about 25 neurons. The budget stop under-counted,
     and the summary under-reported.
   - **The fix:**
     - `SuggesterResult`'s `transport-error` gains an optional `usage`, set only on truncation.
       A non-OK status, a thrown fetch or a timeout has no billed body, so it reports none.
     - `runNetContentSuggestions` counts that usage (reported neurons, else the rate-table
       estimate) through a shared `addUsage` helper, then still writes no row and still counts
       the call as failed.
   - **Tests:** four new tests.
     - `tests/net-content-suggester.test.ts`: truncation carries the measured usage; a 429
       carries none.
     - `tests/net-content-run.test.ts`: a truncated 25-neuron call plus a 5-neuron reply reaches
       a 28 budget and stops the third call; a truncated call with no reported neurons is
       estimated from the rate table.
     - With the `lib/` change reverted, three of the four fail. The 429 case passes either way,
       because it pins behaviour that was already correct.
   - **Unchanged, and still worth a look:** three truncations in a row end the run as "transport
     errors", which is the intended guard against a model that can't answer. A product that
     always truncates is still retried, and paid for, on every run, but now at a counted cost.
     With reasoning off, truncation wasn't seen again on dev.
2. **Image + reasoning-off, proven at Validate (2026-09-26) — see R29 below.** No longer shaky.
3. **The label check's parser** (`lib/net-content-label-check.ts`) was tested against R12's table
   and the dev catalogue's own label shapes (`£8.99 / 5kg`, `£4.49 / 2L`, `£7.48 / litre`).
   Production's 80 Aheed products have their own labels, 41 of which state a pack size, and they
   have not been run through it.
4. **Edit that changes the unit** (2 LITRE → 2000 MILLILITRE) was proven live. Edit's *refusals*
   (`0`, `1.5`) and "identical values produce `ACCEPTED`" are unit-tested only.
5. **Vendor scoping of the queue** (R18/R19/R21) is unit-tested with a stubbed client. It hasn't
   been proven live with a second vendor's row. `demo-srimart-admin` exists on dev for that.
6. **Model output drifts.** The same prompt produced different JSON shapes across Build's probes
   (`evidence` vs `evidenceSource`, and a null `amount` with `unit: "EACH"`). The validator is the
   guard, so a new shape becomes `NO_ANSWER`, not a bad row. A spike in `NO_ANSWER` on a later run
   more likely means shape drift than hard products.

## Fix (2026-09-25, from a fresh Validate pass)

- **R34 — `tests/product-image.test.ts` failed `npx vitest run`.** `it("exports exactly the seven
  actions", ...)` hard-coded the file's export list and was never updated for `toggleConfirmedPhoto`
  (R8), so it asserted seven names against an eight-name module. **This was the check, not the
  artifact** — `toggleConfirmedPhoto` is a real, required action (R8's gating gate and vendor scope
  were already correct and unit-tested elsewhere); nothing in `features/admin/product-image.ts`
  changed. Fixed by adding `"toggleConfirmedPhoto"` to the expected array and renaming the test to
  "exports exactly the eight actions". Confirmed alone (`npx vitest run tests/product-image.test.ts`,
  34/34) before the full re-run. No `CHANGELOG.md` entry: no observable behaviour changed.
- **`validation.md`'s R32 row named a grep pattern that could never match.** It grepped
  `ARTIFACT_INDEX.md` for the literal string `p900-ai-net-content-suggestions-plan` — a front-matter
  `id` value — but `kms/scripts/build-index.ts` never renders a doc's front-matter `id` as text
  anywhere in its output; it lists the title as a link to the file's path instead. Checked against
  four other specs' `id` values in the current `ARTIFACT_INDEX.md`: none appear literally either, so
  this is a pre-existing characteristic of the generator, not something this slice changed. **The
  row itself was wrong, not the artifact** — R32's actual requirement ("`ARTIFACT_INDEX.md` listing
  this slice's `plan.md`") was already satisfied (confirmed live: the row is present, linking
  `specs/2026-09-25-p900-ai-net-content-suggestions/plan.md`). Fixed the row's command to grep the
  file path instead, which does match.
- **Not fixed, flagged instead: dev's three `pg_trgm` indexes are missing.** R3's verification step
  (`scripts/verify-unit-price-sort.ts`) failed on `Order_guestEmail_trgm_idx` being absent; a direct
  query confirmed all three indexes from `20260820143949_p7_5de_order_search_trigram` are gone from
  `ep-dry-morning-zab7dx08`, even though `prisma migrate status` still lists that migration as
  applied. `#900`'s own migration contains no `DROP` and never touches `Order`/`User` (confirmed by
  reading its SQL), so this is pre-existing dev-environment drift, not something this branch caused
  or can fix by editing this slice's code — it is the exact GAP-011 trap CLAUDE.md warns about, just
  discovered here. Left as-is and reported to the owner rather than "fixed" under this issue's scope;
  it needs its own `/propose` (re-run the hand-authored migration's `CREATE INDEX IF NOT EXISTS`
  statements against dev, or open an issue to do so) rather than an improvised fix inside `#900`'s
  Fix stage.
- **R29 — closed at Validate (2026-09-25 session), evidence gap only, no code defect.** That pass
  proved the upload → `STAFF_UPLOAD` → `choosePhotoEvidence` → `productImageId` wiring live
  end-to-end, using a placeholder image in place of a real front-of-pack photo (that environment had
  no outbound access to fetch one).

## Validate (2026-09-26) — R29 re-run with a genuine photo, and R27's open question closed

wiring-only proof.

  `3017620422003`, front JPEG — 33,108 bytes, byte-identical to Build's own record), converted it to
  WebP with `sharp` at the same 1200px edge the client does (`fitWithinEdge`), which produced a

- **Uploaded it through the real flow, not a shortcut**: `requestImageUpload` for a dev Aheed product

  row reads `source = STAFF_UPLOAD`, exactly as R4/R29 require.
- **Ran `scripts/suggest-net-content.ts --product <id> --include-attempted --limit 1`.** Result:
  `400 GRAM`, `evidenceSource: PHOTO`, `evidenceText: "400G"`, `productImageId` equal to the upload's
  own id — matching the printed pack size (Nutella is sold in 400 g jars) and closing R29's evidence
  condition for real.
- **This also closes R27's open question ("image + reasoning-off has never been run").** Latency was
  10.0 s (higher than R27's reasoning-on ~3.2 s figure, but reasoning was off here as it is for every
  production run), 689 input / 44 output tokens, ~7.5 neurons, no truncation. Gemma 4 correctly reads

- **Tooling note, not a repo defect:** the presigned PUT's binary body failed silently under this

  Node `fetch()` script sending the identical bytes to the identical URL succeeded immediately

  from the existing FormData-closure trap the playbook already documents.
- **Left as found:** the test upload and its resulting suggestion row were left in dev rather than
  reverted, consistent with how R28/R30's own live evidence was left in place — this is pilot data by
  design, not a side effect to clean up.
