## What changed and why

    `findUnique({ where: { vendorId }, select: { vendorId: true } })` first. With no row it returns

## Decisions taken during the build

- **The `#1161` error copy** names no store and no remedy beyond the fact. A platform admin is the
  only person who can reach that branch, and creating the row is a provisioning job with no UI
  today.
- **The `#1162` id keeps the `cart-note-` prefix** in front of `useId()`'s output, so the DOM still
  reads as a note field when inspected. React 19's `useId()` returns a value like `«r0»` or `:r0:`.
  That is valid in an `id`, and `htmlFor` matching doesn't care. It is not a valid bare CSS
  selector, but nothing selects by this id.
- **No `surface` prop fallback was needed.** `useId()` worked in this Server Component on the first
  try, both in the jsdom test and in typecheck.
- **`#1119`'s `null` also covers "reachable with zero datasets".** The issue only named the
  `emptyStatus()` path. `plan.md` and R9 fixed this at Spec, and the build follows it.
- **Filed `#1165`** (Backlog, P10): alerting when the reference database stops answering between
  deploys. It was a deliberately excluded item with no other home once `#1119` closes.
- **Not filed:** "provision a missing `VendorConfig` row". There is no vendor-creation flow outside
  `prisma/seed.ts` and two verify scripts, so the gap has no surface to land on. `#1161`'s refusal
  is the whole answer until an onboarding flow exists.
