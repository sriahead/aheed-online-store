# Dependency pin ratification (build notes)

Slice for **`#491`**. Spec commit `3eced79`, implementation commit `da666f7`, branch
`feature/dependency-pin-ratification` off `origin/staging`.

## What changed and why

Three declared specifiers lost their range operator, one test file was added, one paragraph of
`CLAUDE.md` was rewritten, and `package-lock.json` was re-synchronised. **No runtime code was
touched** — the versions being pinned are the versions that were already installed and already
running in production, so this slice deliberately produces no behavioural diff.

**The framing matters more than the diff.** `#491` was filed as dependency *drift*. It was not.
Both DB pins moved in a single deliberate commit, `ac3f0d6` (2026-08-14, "Fix: Cloudflare Connection
Exhaustion / Docs updated") — the same commit that rewrote `lib/db.ts` to introduce the hybrid
`getPrisma()` (HTTP) / `getPrismaWs()` (WebSocket) strategy that `CLAUDE.md` now documents as
authoritative, and that added the `tests/regression/test-checkout-loop.js` and `test-crash.js`
harnesses. That commit edited `CLAUDE.md` too — but only the hybrid-driver section, not the pin
paragraph. So the lockfile was the current artifact and the doc was the stale one, which is why this
slice ratifies rather than reverts. Pinning back to `0.10.4` / `6.19.3` would have undone the
dependency half of a fix for a real production problem on the strength of a paragraph nobody
updated.

**`package.json` (R1, R2, R2a).**

```
@neondatabase/serverless  ^1.1.0  -> 1.1.0
@prisma/adapter-neon      ^7.9.1  -> 7.9.1
@prisma/client            ^6.19.3 -> 6.19.3
```

**`package-lock.json` (R4, R4a).** Re-synchronised via `npm install --package-lock-only`. This was
**not** optional — see the first deviation below.

**`tests/dependency-pins.test.ts` (R5-R7).** Asserts two independent properties per package: the
installed version equals the documented literal, and the declared specifier carries no range
operator. Both are needed. Checking only the installed version would have passed cleanly throughout
the entire three weeks of drift, because `^1.1.0` resolved to `1.1.0` the whole time — the lockfile
looked correct and the manifest was the thing that had quietly become permissive.

**`CLAUDE.md` (R8-R12a).** The paragraph carried **four** false claims, not the one `#491`
described. Two were the pins themselves. The third was `@cloudflare/workers-types` "must match
wrangler's major (v5)", false in both halves — types resolve to `5.20260804.1` against wrangler
`4.119.0`, so the majors do not match and the parenthetical `(v5)` does not describe wrangler. It is
now recorded as an *observed pairing* rather than an asserted rule, because this slice has not
verified any general relationship between the two. The fourth was the suite size, recorded as
`74/874`; measured `77/903` after this slice (`76/897` before it).

That fourth one is the one worth understanding rather than just fixing. `CLAUDE.md` teaches the file
count as *the tell* for its silent worker-startup trap — "know what the suite's file/test totals
should be and treat any shortfall as a non-result". A stale count does not merely age badly, it
**disables the detection it exists to provide**: a validator who believed `74` would have read a
three-file shortfall as the expected number and passed a run in which three files never executed.

**`ARTIFACT_INDEX.md` and `app/(admin)/staff/runbook/docs.ts`** were regenerated by
`npm run kms:build-index`, because this slice's `plan.md` is a new KMS artifact. These are the sole
`app/`-prefixed path in the diff and are build output, not runtime code (R13 names this exception
explicitly).

## Decisions taken during the build

- **Pinned `@prisma/client` as well, which the `/propose` summary did not name.** That summary said
  "the two drifted packages", but the approved `requirements.md` defines "the three pinned packages"
  as including `@prisma/client`, and R6 asserts the no-range property for all three. Pinning it is
  also what keeps `#560`'s straddle from moving silently — the whole risk is the *relationship*
  between adapter and client majors, and leaving the client on a caret would have left half of that
  relationship free to drift. It additionally keeps `package.json`'s `allowScripts` key
  `@prisma/client@6.19.3` matching what actually resolves; `CLAUDE.md` requires those keys to be
  exact and to match the resolved version, so a floating client would eventually break approval of
  install scripts.
- **Did NOT pin `prisma` (the CLI/generator), which is still `^6.19.3`.** Out of scope: R3 and R6
  name three packages and the CLI is not among them, and Build's rule is to build what
  `requirements.md` says rather than what seems adjacent. Recorded in `CLAUDE.md`, in the test's
  docstring, and filed as **`#561`** rather than silently added.
- **Kept npm's canonical lockfile output rather than hand-editing two specifier strings.**
  `npm install --package-lock-only` also materialised six previously-absent entries. Hand-editing
  only the mirror lines would have produced a lockfile npm did not generate and would re-add on the
  next install anyway. Verified the six are inert (below).
- **Wrote the test as data-driven over a `PINNED` map** rather than three hand-written assertions,
  so adding a fourth package is a one-line change, and made the failure messages explain *why* the
  rule exists rather than just reporting a mismatch — this rule has already been broken once by
  someone who had no reason to know it mattered.
- **Recorded `@cloudflare/workers-types` as observed rather than asserting a corrected rule.** The
  tempting fix was to write "workers-types is one major ahead of wrangler". This slice has two data
  points and no evidence that is a maintained invariant, and inventing a replacement rule is how the
  original false sentence got written in the first place.

## Deviations from the spec

Three spec corrections, all made during Build and all disclosed rather than quietly absorbed. Two of
them mean the committed `requirements.md`/`validation.md` differ from what was approved at `/spec`.

**1. R4 demanded an EMPTY `package-lock.json` diff. That was wrong, and following it would have
broken CI on every workflow.** `package-lock.json` mirrors the declared specifiers in its root
`packages` root entry, so editing `package.json` without re-syncing leaves manifest and lockfile
disagreeing — and **all eight workflows run `npm ci`**, which refuses to install when they disagree.
The original R4 mandated exactly that broken state. R4 now requires a re-sync in which **no resolved
version changes anywhere in the tree**, and **R4a** was added asserting `npm ci` itself exits 0.

Verified rather than reasoned: a real `npm ci` exits 0, and after that clean install the three
packages resolve to `1.1.0` / `7.9.1` / `6.19.3`. The only lockfile content changes are the three
root-mirror specifiers plus **six purely additive entries**, all optional bundled dev dependencies
nested under Tailwind's wasm fallback:

```
node_modules/@tailwindcss/oxide-wasm32-wasi/node_modules/@emnapi/core           1.11.1
node_modules/@tailwindcss/oxide-wasm32-wasi/node_modules/@emnapi/runtime        1.11.1
node_modules/@tailwindcss/oxide-wasm32-wasi/node_modules/@emnapi/wasi-threads   1.2.2
node_modules/@tailwindcss/oxide-wasm32-wasi/node_modules/@napi-rs/wasm-runtime  1.1.4
node_modules/@tailwindcss/oxide-wasm32-wasi/node_modules/@tybys/wasm-util       0.10.2
node_modules/@tailwindcss/oxide-wasm32-wasi/node_modules/tslib                  2.8.1
```

**Zero `CHANGED` and zero `REMOVED` entries.** `validation.md`'s R4 row refers here for the exact
comparison snippet; it is:

```js
const fs = require("fs");
const sp = "<a Windows-visible scratch dir>";
const a = JSON.parse(fs.readFileSync(sp + "/lock-before.json", "utf8"));
const b = JSON.parse(fs.readFileSync("package-lock.json", "utf8"));
let c = 0;
const keys = new Set([...Object.keys(a.packages), ...Object.keys(b.packages)]);
for (const k of keys) {
  const va = a.packages[k] && a.packages[k].version;
  const vb = b.packages[k] && b.packages[k].version;
  if (va !== vb) {
    console.log(va === undefined ? "ADDED" : vb === undefined ? "REMOVED" : "CHANGED", k, va || "-", "->", vb || "-");
    c++;
  }
}
console.log("entries differing:", c);
```

Populate it with `git show origin/staging:package-lock.json > "$SCRATCH/lock-before.json"`.
**Use a real Windows-visible path** — node on this machine resolves a bash `/tmp/x.json` to
`E:\tmp\x.json` and fails with `ENOENT`, which cost a round trip during Build.

**2. R8 banned the literal string `0.10.4` from the dependency section.** Following it literally
would have forced deleting the from-version in "raised from `0.10.4` in `ac3f0d6`" — the single fact
that makes the correction comprehensible, and which R9 effectively requires. R8 now forbids `0.10.4`
as a **current** pin while explicitly permitting the historical reference.

**3. R13's expected-path list omitted `package-lock.json`.** A consequence of correction 1; added.

No requirement was reinterpreted to make the implementation easier, and nothing outside
`requirements.md` was added to the product.

## Known-shaky areas

Point validation here first.

1. **The six added lockfile entries are the least-examined part of this diff.** They were verified
   as additive-only and as optional/dev/bundled, and `npm ci` succeeded with them, but nothing
   exercised the Tailwind wasm32-wasi fallback path itself — nothing does, on x64 runners. If a
   build behaves oddly on an unusual architecture, look here. The strongest available check is R4's
   comparison showing zero `CHANGED`/`REMOVED`.

2. **`npm ci` leaves the repo un-typecheckable until `npm run db:generate` runs, and the failure
   looks catastrophic.** After the clean install, `npm run typecheck` reported **169 errors** across
   `lib/repositories/*`, `prisma/seed.ts` and `scripts/*` (`TS2347 Untyped function calls may not
   accept type arguments`, `TS7006 implicitly has an 'any' type`). Every one vanished after
   `npx prisma generate`. This is an artefact of the clean install, **not** a regression from this
   slice, and CI is unaffected because `quality.yml` runs `npm ci` then `npm run db:generate`
   explicitly. A validator who runs `npm ci` and then `typecheck` without generating will otherwise
   conclude this slice broke the repository.

3. **The suite-size numbers now written into `CLAUDE.md` are measurements from one machine on one
   day.** `77 files / 903 tests` was observed directly (and `76/897` immediately before adding the
   test file), run alone, exit 0. They will go stale the moment any slice adds a test file — that is
   inherent, and the mitigation is that they are now correct *and* the reason they matter is written
   next to them. CI on Linux remains the authority.

4. **The worker-startup trap fired during this Build in a way `CLAUDE.md` did not describe, and the
   corrected description is itself from a single observation.** The first full-suite run gave
   `66 files / 807 tests` with **10** `Failed to start forks worker` errors and **exit 1** — not the
   `exit 0` `CLAUDE.md` documented — despite vitest running **alone**, immediately after the
   `kms/site-internal` Next build had *finished*. No orphaned `node.exe`/`workerd.exe` processes
   existed (checked). Simply re-running gave a clean `76/897`. Both refinements are now in
   `CLAUDE.md`, but they rest on one occurrence; if validation sees this trap behave differently
   again, the description is the thing to correct, not the run.

5. **R7's mutation check must leave the tree clean, and the obvious way to restore is wrong.**
   `git checkout -- package.json` would discard *all* of this slice's pins if run while they are
   uncommitted. Copy the file aside and copy it back instead. After running R7, confirm
   `git status --porcelain package.json` is empty before continuing.

6. **Nothing proves the adapter-7-against-client-6 pairing is *intended* by Prisma, only that it
   works.** There is no declared contract to check: `@prisma/adapter-neon@7.9.1` publishes no
   `peerDependencies` at all. The evidence is roughly three weeks of production, every P9.1 payment
   slice, `#454`, and `#489`'s ~2,000-product write. That is strong empirical evidence and zero
   contractual evidence, and it is the whole reason `#560` exists. This slice contains the risk (the
   pairing can no longer move silently) without resolving it.

7. **`prisma` (the CLI) still floats at `^6.19.3` while `@prisma/client` is now fixed.** `npm ci`
   pins it from the lockfile so CI cannot drift, but a local `npm install`/`npm update` can now move
   the generator away from the pinned client in a way it could not before this slice, when both
   carried the same range. Low likelihood, disclosed in `CLAUDE.md` and filed as **`#561`**.
