# #964, #966, #968 — Mobile tap targets, postcode autofill, discount-code copy (plan)

Slice 4 of the mobile programme that came out of the seventh Discover pass
(`docs/research/discovery-log.md`, 2026-10-02). Slices 1–3 (`#960`–`#962`, `#958`/`#959`,
`#956`/`#967`) are in production. Approved at `/propose` on 2026-10-04.

**Goal:** finish the touch-target work `#961` started, so that no storefront control a shopper
taps on a phone or tablet is smaller than 44×44 CSS px. Close the two small follow-ups found along
the way: a postcode input with no autofill token, and one wrong sentence in the shopper guide.

## 1. Scope

### #964 — the `tap` token on the remaining controls

`#961` added `--spacing-tap: 2.75rem` (44px, `design-system/tokens/tokens.css`). It generates
`h-tap`, `w-tap`, `size-tap`, `min-h-tap` and `min-w-tap`. It applied them only to the controls its
own measurements named. This slice applies the same rule, **below `lg` only**, to every control
below. Each surface gets a `data-tap-surface` hook so the measuring script can find it:

| Surface (`data-tap-surface`) | File | Controls | Today (from classes) |
|---|---|---|---|
| `location` | `components/layout/LocationControl.tsx` | header Collect/Delivery toggles, the pencil (change postcode), the single Delivery button | `px-3 py-1.5 text-xs`, about 28px tall |
| `location-dialog` | same file, inside the `<dialog>` | postcode input, its submit button, the close button | `py-2.5 text-sm`, about 40px |
| `filter-chips` | `components/product/FilterChips.tsx` | each applied-filter chip, "Clear all" | `px-3 py-1 text-sm`, about 30px |
| `filter-panel` | `components/product/FilterPanel.tsx` | the mobile disclosure `<summary>` only | `px-4 py-3`, about 48px (may already pass) |
| `subcategories` | `components/product/SubcategoryLinks.tsx` | each subcategory pill | `px-4 py-2 text-sm`, about 38px |
| `collections` | `components/product/CollectionNav.tsx` | each collection link | `px-3 py-2 text-sm`, about 36px |
| `pagination` | `app/(storefront)/categories/[slug]/page.tsx`, `app/(storefront)/search/page.tsx` | Previous page, Next page | `px-4 py-2`, about 40px |
| `cart-line-controls` | `components/cart/CartContents.tsx` | per line: decrease, increase, remove | `p-1` around a 12–14px icon, about 20px |
| `scroller-arrow` | `components/layout/HorizontalScroller.tsx` | the left and right arrow buttons | `h-8 w-8`, 32px |

The "Today" column is an estimate from the class strings. Build measures the real numbers (section 3).

Some facts behind the scope:

- **`#964` names "`DepartmentScroller` arrows", but the arrows live in `HorizontalScroller`.** They
  moved there in `#511`. `ProductRow` and `BundleRow` use the same component, so their arrows grow
  too. That is intended: one arrow, one size.
- **`CartContents` renders in two places**: the header's cart drawer (`Header.tsx:331`) and `/cart`
  (`app/(storefront)/cart/page.tsx:88`). One edit covers both. The script measures it on `/cart`,
  because opening the drawer would need another script flag.
- **`FilterPanel` renders its form twice**, once in a mobile `<details>` and once in a desktop aside.
  Only the mobile `<summary>` is in scope. The controls *inside* the opened panel are not (see
  Deliberately excluded).

### #966 — postcode autofill

`LocationControl.tsx:196`'s `<input name="postcode">` gets `autoComplete="postal-code"`, and
`tests/autocomplete-tokens.test.ts` asserts it. The issue saw "a second postcode input" on every
page. It is the same element: `Header.tsx` mounts `LocationControl` twice, at `:257` (inline, from
`sm`) and `:368` (the phone row). P8.5f moved the homepage checker into the header, so there is no
separate landing input. Checkout's postcode already has the token (`#958`).

### #968 — shopper guide copy

`docs/shopper-help/shopping-guide.md:32` says a promotional code is applied "in your cart". The field
is on checkout (`components/checkout/CheckoutForm.tsx`, "Discount code"). The bullet is corrected.
The runbook copy in `app/(admin)/staff/runbook/docs.ts` is regenerated by `kms:build-index`, never
hand-edited.

## 2. How the controls grow

These patterns follow `specs/design-system.md`'s "Touch targets" section and `#961`'s precedent:

- **Below `lg`** the control is at least 44px on each side. **From `lg`** it keeps today's size
  exactly. For example, `min-h-tap lg:min-h-0` on a pill, or `size-tap lg:size-8` on an arrow.
- **A small visual can keep a large hit area.** The remove icon, the stepper icons and the arrows
  keep their visible glyph or circle size. It is the *button* that grows, by padding or a fixed
  `size-tap`, as the Quick View button did in `#961`.
- **The chip and pill rows grow in height, not in item count.** `min-h-tap` with `items-center`
  keeps one line of text. Build may tighten `gap-*` between items to recover height. It may not
  remove a control or hide its text.
- **Scroller arrows must not widen the page.** Today a 32px arrow sits half outside the track
  (`-translate-x-1/2`). A 44px button placed the same way overhangs 22px. If that overhang widens
  the document past the viewport, Build insets the arrows below `lg` instead. R10 checks the result,
  not the method.

## 3. Measuring, and the baseline

The instrument is `scripts/verify-mobile-layout.ts` (`#960`–`#962`, extended by `#958`/`#959` and
`#956`). This slice adds three things to it:

- `tapTargets`: every `a`, `button`, `summary` and visible `input` that is a `[data-tap-surface]`
  element or sits inside one, with its surface, name and size;
- `firstCardTop`: the first product card's top, in document coordinates;
- `--open-location`: opens the displayed `LocationControl`'s dialog before measuring.

**Build order matters for the baseline.** The hooks (`data-tap-surface`, `data-location-dialog`)
and the script change land first, with **no class change**. Build then runs the baseline commands
(validation.md, "Baseline") and records the raw JSON lines in `build-notes.md`. Only then does it
change sizes. Without the hooks, the old code has nothing for the script to group by surface.
R11 and R12 compare against that recorded baseline.

**Density cost.** Taller pills and chips push the product grid down, which works against `#960`'s
header trim. On the Aheed category page with a filter applied, R11 caps the first card's downward
move at **60px at 390px wide**. The cap was 40px at `/spec`. Build measured +56 (Aheed) and
+46 (SriMart): about 14px for the location row, 14px for the chips, 6px per subcategory row and
8px per collection row. Tightening `gap-*` recovers only about 8px. On 2026-10-04 the owner chose
to accept the measured cost and set the cap at 60, rather than make the collection links a
swipeable row. Build does not drop a control to meet the cap.

## 4. Deliberately excluded

- **Controls inside the opened mobile filter panel** (checkboxes, range inputs, Apply). They are
  form fields with their own label hit areas, and `#964` did not list them. If measurement shows a
  real problem there, it gets a new issue.
- **Staff panel controls.** `#964` is storefront-only, and the staff panel is a desktop-first tool.
- **The cart drawer's own close button, and the header search field.** Neither is listed in
  `#964`. The search field is already full width.
- **`pointer-coarse:` instead of `lg`.** It would be more exact, but no tool available to validation
  can emulate a coarse pointer. `#961` settled this in `specs/design-system.md`.
- **WCAG framing.** Every control already meets SC 2.5.8 (AA, 24×24). This slice is SC 2.5.5 (AAA)
  and platform guidance, so it is a usability fix, not a compliance one.
- **`#973`/`#972`** (checkout total preview, self-referral), **`#957`** (reorder notice) and **`#395`**
  (bottom nav). These are separate, later slices.
